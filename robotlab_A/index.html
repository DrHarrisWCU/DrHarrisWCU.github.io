Setup, once, about 10 minutes

On many Linux systems (Debian, Ubuntu and their relatives) and on Homebrew's Python for macOS, pip refuses to install libraries system-wide, and the error says "externally-managed-environment". Windows usually does not refuse, but the fix is good practice everywhere: give each project its own private virtual environment, a folder holding just that project's libraries. You make it once, then switch it on each time you open a terminal.

Name the folder after the project. The terminal prompt shows that name in brackets, so with several projects open you can see which one is active. Here it is robotlab-a-env. For your next project, use a different name.

  1. Unzip the scripts zip (linked beside this page) into a new folder, for example robotlab, and open that folder in your editor. In VS Code, choose File, Open Folder, answer "Yes, I trust the authors" if asked, then click the layout button circled below to show the terminal panel.
  2. Create the environment, once: 
    python3 -m venv robotlab-a-env          # Linux or macOS
py -m venv robotlab-a-env               # Windows PowerShell
  3. Switch it on. The prompt then starts with (robotlab-a-env): 
    source robotlab-a-env/bin/activate       # Linux or macOS
robotlab-a-env\Scripts\Activate.ps1      # Windows PowerShell
  4. Install the libraries, only while it is on: 
    pip install dynamixel-api numpy scipy
    dynamixel-api is a small friendly layer for one servo at a time. It pulls in dynamixel-sdk, ROBOTIS's own library, which a few scripts here use directly.
  5. Tell your editor to use it: press Ctrl+Shift+P, choose "Python: Select Interpreter", and pick the one inside robotlab-a-env. Then the editor's run button and its terminal agree.
  6. Check the setup: python check_setup.py. It prints your Python and library versions and the serial ports it can see.

Every new terminal, repeat step 3. If pip says "externally-managed-environment", the environment is off. Do not work around it with --break-system-packages.

If setup goes wrong

On Ubuntu or Debian, if venv fails, run sudo apt install python3-venv first. On Windows, if PowerShell refuses to run the activate script, run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once. Find the port name on Linux with ls /dev/ttyACM* /dev/ttyUSB* (an OpenCR usually appears as ACM, a U2D2 as USB). On Windows, read the COM number in Device Manager. If it is not /dev/ttyACM0, change the PORT = ... line at the top of each script. python check_setup.py lists the ports it can see, and the top of Wizard's device list (Module 1) shows the name too.

Written against dynamixel-api 1.0 (for one servo, as in Module 2) and dynamixel-sdk 4.x (for the arm, in later modules), both speaking Protocol 2.0. If a library update breaks something, move_one.py and bus.py are the only files that touch the libraries. The register addresses sit in one block at the top of bus.py.

Module 1 of 13 · about 25 minutes

Give every servo a name

Every new DYNAMIXEL ships with ID 1. Servos share one set of wires, so two servos with the same ID answer the same packet at the same moment and corrupt each other. Before anything moves, each servo needs its own ID.

By the end: two servos with two different IDs, set the right way, and a scan that proves it.
First, connect the hardware

A DYNAMIXEL needs two things on the same 3-pin cable: data from your computer, and 12 V power. The adapter does the data. Where the power comes from depends on which board you have. Both ways below end the same: your computer sees one serial port, and every later step is identical.

Way 1: U2D2 with the U2D2 Power Hub Board

The U2D2 alone is not enough. It is only a USB to serial converter and does not power the servos. ROBOTIS sells the U2D2 Power Hub Board for that: it powers the U2D2 and feeds power into the servo cables. Plug the U2D2 into the hub board, run the 12 V supply into the board's barrel jack, and plug the servo cables into the board's 3-pin ports. (A standalone power hub, such as the SMPS2Dynamixel, or a spliced power lead can do the same job, but the hub board is the simplest.) Use the U2D2's 3-pin TTL connection, which is what the XL430 speaks.

The U2D2 shows up as a USB serial port: /dev/ttyUSB0 on Linux, a COM port on Windows. On Linux there is one extra step. The USB driver holds data for 16 milliseconds by default, which makes every read and write slow. That would wreck the timing experiments in Optional B and Module 4. One way to set it to 1 ms, until you unplug the adapter:

echo 1 | sudo tee /sys/bus/usb-serial/devices/ttyUSB0/latency_timer

For a permanent fix, a one-line udev rule does it (search "FTDI latency timer udev Dynamixel"). Windows and macOS students can skip this.

Way 2: OpenCR 1.0

The OpenCR is a robot controller board with its own processor. Loaded with a small program called usb_to_dxl, it passes bytes between USB and the servo bus, so it acts as the adapter. You load that program once, from the Arduino IDE. If someone already did this to your board, and Wizard finds your servos, skip to the power step.

  1. Install Arduino IDE 2.0 or newer from arduino.cc/en/software. The OpenCR board package does not work with the legacy 1.x IDE.
  2. Open File, Preferences. In "Additional boards manager URLs" paste: 
    https://raw.githubusercontent.com/ROBOTIS-GIT/OpenCR/master/arduino/opencr_release/package_opencr_index.json
    If that link fails, follow the instructions for your operating system on the ROBOTIS OpenCR 1.0 page.
  3. Close the window. The board support should install by itself. If it does not, open Tools, Board, Boards Manager, search for "OpenCR" and click Install.
  4. Choose Tools, Board, OpenCR, OpenCR Board. Then Tools, Port, and pick the port your OpenCR is on.
  5. Unplug every servo from the OpenCR. With a servo attached, the upload can hang in an endless loop, because the servo bus interferes with the handshake between the board and the computer.
  6. Open File, Examples, OpenCR, 10. Etc, usb_to_dxl, and click Upload.
  7. When the upload finishes, now plug the servo in. Plug the 12 V supply into the OpenCR's barrel jack, and slide its power switch to ON (circled in the photo). The OpenCR then feeds that voltage to its servo ports. USB carries data and powers the board's logic, not the servos.

The OpenCR shows up as /dev/ttyACM0 on Linux or a COM port on Windows, and it does not have the Linux latency problem above.

Either way

  • XL430-W250 is a 12 V model: the "W" in its name means 12 V. Keep every other voltage away from it.
  • Plug in the cables with the power off. Switch the 12 V on last, and off first.
  • The servo has two identical 3-pin sockets. A second servo goes in the free socket of the first (a daisy chain). Both are on one bus.
  • On power-up each servo flashes its LED once. No flash means no power.

Do it on the real servo, with Dynamixel Wizard 2.0

Wizard is the maker's free point-and-click program for DYNAMIXEL servos. It runs on Windows, macOS and Linux. Download it from the ROBOTIS Wizard 2.0 page. No code in this module.

  1. One servo on the bus. Using the connection above, plug in only one servo, with the 12 V on and the adapter connected to your computer. Name the servos one at a time: a second one with the same ID would answer at the same moment and corrupt the replies.
  2. Scan. Open Wizard and click Scan. A progress window tries one port and baud rate after another. The "Connection failed" lines for ports like ttyS0 are normal. When your servo appears in the list, click Skip to stop the scan. A new servo shows up as ID 1 at 57600 bps. If nothing appears, see the checklist below, and look in Options for the ports and baud rates the scan covers.
  3. Select it. Click the servo in the left list. The dashboard shows its ID, baud rate, protocol, voltage, load and temperature, and a dial with Torque and LED switches. (The Control Table tab lists every register you will meet in Module 3.)
  4. Give it its own ID. Choose the new number in the ID box and click Save. Settings like ID only unlock while torque is off, which is the default. Use 1 for the yaw joint, which spins the whole arm, and 2 for the pitch joint. Tape the number on the servo. Do each servo alone, never repeating a number.
  5. Test it, gently. Toggle the LED and see it light. Then toggle Torque and click the dial a small angle from where it is now. The motor does not move unless torque is on. It goes to exactly the angle you give, whatever it is attached to, so keep fingers and cables clear. You just did by hand what Module 2 does from Python.
  6. Put them on one bus. When every servo has its own ID, daisy-chain them (the second plugs into the first's free socket) and scan again. Both must appear. Select each in turn and flash its LED or nudge it. Do not click Save on the ID again now: with both attached, you would have to separate them again. The top line of the list is your serial port name, for example ttyACM0 on Linux or COM4 on Windows. Write it down: every script needs it.
  7. Close Wizard before you run any Python. A serial port serves one program at a time, and the scripts fail with a port error while Wizard holds it.

Module 2 of 13 · about 25 minutes

Talk to a servo

A hobby servo reads one pulse width. A DYNAMIXEL is a small computer on a shared serial bus, so you send it packets. Each servo has an ID and answers only when addressed.

By the end: build a real Protocol 2.0 packet by hand, decode one, and explain why a servo ignores a damaged packet.
The packet, byte by byte

Everything the computer says to a servo is a packet: a short run of bytes on the wire with a fixed layout. You will never type one by hand, because the library builds it. But you should know what is inside, so that a failed read or a strange error is not a mystery. This is Protocol 2.0, the one the XL430 speaks.

An instruction packet, from the computer

FieldBytesWhat it holds
Header3FF FF FD. A fixed pattern that says "a packet starts here". Every servo watches the wire for it
Reserved100. Always zero
Packet ID1Which servo this is for, 0 to 252. FE (254) means everyone
Length2How many bytes follow the length field: the instruction, the parameters, and the two CRC bytes
Instruction1What to do: 01 Ping, 02 Read, 03 Write, 83 Sync Write (many servos in one packet)
Parameters0 or moreThe details. For Read and Write, first the register address (2 bytes), then for a Read the byte count, or for a Write the data
CRC2A check value computed from every byte before it

Any number wider than one byte goes out low byte first (little-endian). The address 116 is 0x0074, so it travels as 74 00. A goal of tick 3072 is 0x00000C00, so its four bytes are 00 0C 00 00.

Worked example. "Servo 1: write goal position 3072." Goal Position lives at address 116 and is four bytes wide, so there are six parameter bytes. The length is the instruction (1) plus six parameters plus two CRC bytes, which is 9.

That is 17 bytes. A Read is the same layout with instruction 02 and, after the address, the number of bytes you want. A Ping has no parameters at all.

The status packet, the servo's reply

The addressed servo answers with the same frame, but the instruction byte is 55, and the first parameter is an error byte: 00 means all went well. After it come the bytes you asked to read, again low byte first. A servo that hears a packet for a different ID says nothing, and a Write to ID 1 gets a short reply that only holds the error byte.

Two protections

  • Byte stuffing. The header pattern FF FF FD must never appear by accident inside data, or a servo would think a new packet started. When the sender's data happens to contain those three bytes, it inserts one extra FD after them, and the receiver removes it. The length counts the stuffed bytes.
  • The CRC. The sender computes a 16-bit check value from all the bytes before it and appends it. The servo recomputes it from what it received. If the two differ, even by one flipped bit, the servo silently ignores the packet. It does not act on a half-damaged command, and it does not answer. You will not write this calculation: the library does it on every packet. Lab 2.1 lets you break a packet on purpose so you see the effect.

"""Find every servo on the bus, at every common baud rate. This file needs no other file from the zip.
Run it with the servos plugged in and Dynamixel Wizard CLOSED.
Uses dynamixel_sdk, which pip installed together with dynamixel-api.
"""
from dynamixel_sdk import PortHandler, PacketHandler, COMM_SUCCESS

PORT = "/dev/ttyACM0"   # Linux: ttyACM0 (OpenCR) or ttyUSB0 (U2D2). Windows: COM4 or similar. Same name Wizard shows.
BAUDS = [57600, 115200, 1000000, 2000000, 3000000, 4000000, 9600]   # factory baud for the XL430 is 57600

packet = PacketHandler(2.0)
found_any = False
for baud in BAUDS:
    port = PortHandler(PORT)
    if not port.openPort():
        raise SystemExit(f"Cannot open {PORT}. Wrong name, or another program (Wizard?) is using it.")
    port.setBaudRate(baud)
    found, result = packet.broadcastPing(port)       # one packet that every servo answers
    port.closePort()
    for servo_id, (model, firmware) in sorted(found.items()):
        found_any = True
        print(f"baud {baud:>7}: found ID {servo_id:3d}, model {model}, firmware {firmware}")
if not found_any:
    print("Nothing answered at any baud rate. Check power, the cable, the port name, and that Wizard is closed.")

move_one.py: your first real motion. It also stands alone. Run python move_one.py for ID 1, or python move_one.py 2 for ID 2.

"""Move one XL430 with dynamixel_api. This file needs no other file from the zip.
Run:  python move_one.py        (servo ID 1)       python move_one.py 2     (servo ID 2)
Close Dynamixel Wizard first: only one program can hold the serial port.
"""
import sys
import time
from dynamixel_api import XL430W250TConnector

PORT = "/dev/ttyACM0"   # The top of Wizard's device list shows yours. Linux: ttyACM0 (OpenCR) or ttyUSB0 (U2D2).
                        # Windows: COM4 or similar. macOS: /dev/cu.usbmodemXXXX.
BAUD = 57600            # factory setting of the XL430
SERVO_ID = int(sys.argv[1]) if len(sys.argv) > 1 else 1

TICKS_PER_TURN = 4096   # one full turn is 4096 ticks
CENTER = 2048           # tick for "0 degrees". Ticks cannot be negative, so we measure angles from the middle.


def deg_to_ticks(deg):
    """Degrees from center -> goal ticks, clamped into the legal range 0..4095."""
    ticks = round(CENTER + deg * TICKS_PER_TURN / 360)
    return max(0, min(TICKS_PER_TURN - 1, ticks))


def ticks_to_deg(ticks):
    return (ticks - CENTER) * 360 / TICKS_PER_TURN


def wait_until_there(servo, goal_ticks, tolerance=8, timeout=4.0):
    """Poll the real position instead of guessing a sleep time. Returns True if it arrived."""
    start = time.time()
    while time.time() - start < timeout:
        if abs(servo.read_field("present_position") - goal_ticks) <= tolerance:
            return True
        time.sleep(0.02)
    return False


# Leaving the "with" block turns torque off again, so the servo is limp when the script ends.
with XL430W250TConnector(device=PORT, baud_rate=BAUD, dynamixel_id=SERVO_ID) as servo:
    print(f"Connected to servo {SERVO_ID}")
    servo.write_field("profile_velocity", 50)                         # about 11 rpm: smooth and safe (unit 0.229 rpm)
    here = servo.read_field("present_position")
    servo.write_field("goal_position", here)                          # goal = where we are, so torque-on does not jerk
    servo.write_field("torque_enable", 1)                             # now the motor holds its position
    for angle in (0, 30, -30, 0):                                     # degrees from center
        goal = deg_to_ticks(angle)
        servo.write_field("goal_position", goal)
        arrived = wait_until_there(servo, goal)
        measured = ticks_to_deg(servo.read_field("present_position"))
        print(f"goal {angle:+4d} deg = {goal:4d} ticks   measured {measured:+7.1f} deg   {'ok' if arrived else 'did not arrive'}")

What each part does

  • with XL430W250TConnector(...) as servo opens the port and, on leaving the block, turns torque off and closes it. That means the servo goes limp the moment the script ends. A joint holding a load against gravity will sag then, which is why the arm scripts later switch torque off deliberately.
  • write_field("goal_position", n) sends the Write packet from Lab 2.1: address 116, four data bytes. read_field("present_position") sends a Read of address 132.
  • deg_to_ticks is the position calculation. The servo counts 4096 ticks per turn and cannot take a negative goal. We choose tick 2048 as "0 degrees" so angles can be plus or minus, then convert: ticks = 2048 + degrees × 4096 / 360. One tick is about 0.088 degrees. (Lab 2.1 above counts degrees from tick 0, so its 90 degrees is tick 1024. Robot scripts count from the middle, so 0 means straight, and the arm model in Module 5 uses the same zero.) The last line clamps the answer into 0 to 4095, so a typo like 400 degrees cannot send an illegal value.
  • Goal first, torque second. The script copies the present position into the goal before it enables torque, so the servo has nothing to jump to. Then profile_velocity limits the speed (each unit is 0.229 rpm, so 50 is about 11 rpm) and the motion is smooth.
  • wait_until_there reads the position until it is close to the goal. This is better than a fixed time.sleep, because a long move takes longer than a short one, and you also find out if the servo never arrived.

The shared helper for the arm

dynamixel_api talks to one servo per connection, which is ideal for this module. The arm needs both joints on one port, in one packet, so from Module 3 on the scripts use bus.py. It is built on dynamixel_sdk, ROBOTIS's own library, which dynamixel_api itself uses inside. Save it in the same folder as the scripts, then run python bus.py: it lists every servo that answers and where its horn is. It is longer than this module needs. """bus.py: the few Dynamixel calls the later modules need, in one place. Keep it in the SAME folder as the scripts that import it.
It uses dynamixel_sdk, ROBOTIS's own library, which pip installs for you together with dynamixel-api.
Run it on its own to test the connection:  python bus.py
Why not dynamixel_api here? It opens one port connection per servo, and two arm joints must share one port (and one packet).
"""
import os
from dynamixel_sdk import PortHandler, PacketHandler, GroupSyncWrite, COMM_SUCCESS

PORT = os.environ.get("DXL_PORT", "/dev/ttyACM0")   # OpenCR passthrough. U2D2: /dev/ttyUSB0. Windows: COM3
BAUD = int(os.environ.get("DXL_BAUD", "57600"))      # factory setting for the XL430

# Control table addresses (XL430-W250). Look them up again with the e-Manual if your model differs.
ID, OPERATING_MODE = 7, 11
POS_D_GAIN, POS_I_GAIN, POS_P_GAIN = 80, 82, 84
GOAL_PWM, PROFILE_VELOCITY, GOAL_POSITION = 100, 112, 116
MOVING, PRESENT_LOAD, PRESENT_VELOCITY, PRESENT_POSITION = 122, 126, 128, 132
PRESENT_VOLTAGE, PRESENT_TEMP, HARDWARE_ERROR = 144, 146, 70
TORQUE_ENABLE = 64

_port = PortHandler(PORT)
_packet = PacketHandler(2.0)


def to_steps(angle_deg):
    """Joint angle in degrees -> servo ticks. 0 degrees is tick 2048, the same zero the URDF uses."""
    return max(0, min(4095, 2048 + round(angle_deg * 4096 / 360)))


def to_deg(steps):
    return (steps - 2048) * 360 / 4096


def signed(value, nbytes):
    """Registers hold raw bytes. Load and velocity can be negative, so reinterpret as two's complement."""
    top = 1 << (8 * nbytes - 1)
    return value - 2 * top if value >= top else value


def open_bus():
    if not _port.openPort():
        raise SystemExit(f"Cannot open {PORT}. Wrong name, or another program is using it.")
    if not _port.setBaudRate(BAUD):
        raise SystemExit(f"Cannot set {BAUD} baud on {PORT}.")


def close_bus():
    _port.closePort()


def _check(result, error):
    if result != COMM_SUCCESS:
        raise RuntimeError(_packet.getTxRxResult(result))
    if error != 0:
        raise RuntimeError(_packet.getRxPacketError(error))


# ---- generic register access: every other helper is built from these six ----
def write1(servo_id, addr, value): _check(*_packet.write1ByteTxRx(_port, servo_id, addr, int(value)))
def write2(servo_id, addr, value): _check(*_packet.write2ByteTxRx(_port, servo_id, addr, int(value)))
def write4(servo_id, addr, value): _check(*_packet.write4ByteTxRx(_port, servo_id, addr, int(value)))


def _read(fn, servo_id, addr):
    value, result, error = fn(_port, servo_id, addr)
    _check(result, error)
    return value


def read1(servo_id, addr): return _read(_packet.read1ByteTxRx, servo_id, addr)
def read2(servo_id, addr): return _read(_packet.read2ByteTxRx, servo_id, addr)
def read4(servo_id, addr): return _read(_packet.read4ByteTxRx, servo_id, addr)


def ping(servo_id):
    """Model number if the servo answers, otherwise None."""
    model, result, error = _packet.ping(_port, servo_id)
    return model if result == COMM_SUCCESS else None


# ---- the helpers from Module 2 ----
def torque(servo_id, on):
    write1(servo_id, TORQUE_ENABLE, 1 if on else 0)


def goal_pos(servo_id, steps):
    """The goal-position packet from Lab 2.1, built and sent for you."""
    write4(servo_id, GOAL_POSITION, steps)


def present_pos(servo_id):
    return read4(servo_id, PRESENT_POSITION)


def sync_goal(goals):

Turning a raw number into a real unit

The servo does not send degrees or rpm. It sends a whole number, a count of tiny units, and you do the arithmetic. Every register needs the same two steps, and only the first one is sometimes skipped:

  1. Fix the sign (only for registers marked "signed" in the table). A signed register can be negative, but the bus delivers it as an unsigned number. If the raw value is in the top half of its range, subtract the full range. A 2-byte register has a range of 65536, and a 4-byte register has a range of 4294967296.
  2. Multiply by the unit. The "one raw unit is" column says what one count is worth. Position also needs a zero offset first.

The unit column comes from the ROBOTIS e-Manual. Search for "XL430-W250 e-Manual", open the Control Table page, and find the row by its address. The Description column of that page is where "0.229 rpm" and "0.1 %" come from, and the Range column tells you what values to expect. Always check it when you meet a new register or a new servo model.

    return value - 2 * top if value >= top else value

Part 2: torque

The XL430 has no torque sensor. The Present Load register reports how hard the motor is being driven, in percent of its maximum, and while the motor pushes against something that is close to proportional to torque. To turn that percent into newton-metres you need one real force to compare it with. The cheapest force meter in the building is a kitchen scale.

Why not hang weights, as many guides do? The datasheet stall torque is about 1.4 newton-metres. On a 0.10 m lever that is a 14 newton push, about 1.4 kg. Hanging that much weight on a lever is awkward and dangerous, and a few hundred grams only tests the bottom fifth of the range. Letting the servo push down onto a scale reaches much further, and the servo does the loading while you stand clear.

The setup, 10 minutes
  1. Clamp or screw the servo body firmly to the bench. If the body can move, you are measuring the clamp.
  2. Attach a stiff bar to the horn: a printed bar, an aluminium strip or a steel rule. Screw it on. Tape slips.
  3. Set the scale so the bar rests on its platform with the bar horizontal. Put a small flat piece (a coin or a washer) under the bar tip so it touches at one point, and measure r: the distance from the shaft centre to that point, along the bar.
  4. Press the scale's tare button with the bar resting on it, so it reads zero.
  5. The servo pushes in one direction. If, when you run the script, the bar moves away from the scale, stop and run it again with -1 on the end of the command.

The torque at each push is force times lever length: torque = (grams ÷ 1000 × 9.81) × r, in newton-metres. The script does the arithmetic. You supply r and the scale reading.

Safety. The servo can push with real force, and a bar under load can pinch. Keep hands clear while it pushes. The script goes no higher than 50 percent drive, holds each push for four seconds, and pauses between pushes. If the bar or scale slips, stop and fix the setup before pushing harder. The servo shuts itself off on an overload or overheating error, and the script stops when it sees one.

def corners(shape):
    cx, cy = CENTRE
    h = SIZE / 2
    if shape == "square":
        return [(cx - h, cy - h), (cx + h, cy - h), (cx + h, cy + h), (cx - h, cy + h), (cx - h, cy - h)]
    if shape == "triangle":
        return [(cx - h, cy - h), (cx + h, cy), (cx - h, cy + h), (cx - h, cy - h)]
    n = 48
    return [(cx + h * math.cos(2 * math.pi * k / n), cy + h * math.sin(2 * math.pi * k / n)) for k in range(n + 1)]

    pts = corners(shape)

        n = max(1, int(math.hypot(x1 - x0, y1 - y0) / step))
        for k in range(n):
            yield x0 + (x1 - x0) * k / n, y0 + (y1 - y0) * k / n, 0.0
        yield x1, y1, (0.0 if shape == "circle" else CORNER_PAUSE)   # a circle has no corners to wait at

Name the legs and the servos
    
The computer cannot see your robot. It knows servo IDs (numbers stored inside each servo), and it has no idea which leg an ID is on. You and the code have to agree on that, so the agreement is written down in two places and checked once.

    
1. Mark the legs. Seen from above, the legs sit at the four arms of the body plate. The robot will walk toward the gap between two legs, not toward a leg. Choose those two, and call that side the front. Of the two front legs, the one on the left is leg A. Stick a piece of masking tape on it and write A. 2. Give every servo an ID, and write it on the servo. Use Dynamixel Wizard as in Module 1. Hips get the odd numbers and knees the even numbers, and a hip and the knee after it are the same leg: leg A has hip 1 and knee 2, leg B has hip 3 and knee 4, leg C has hip 5 and knee 6, leg D has hip 7 and knee 8. Forward kinematics of one leg
    
Measure from the hip axis, at the underside of the body plate. The knee axis sits 32 mm out and 26 mm down. The leg is 120 mm from the knee axis to the foot. With the hip yaw and the knee angle in degrees:


reach = 32 + 120 * cos(knee)          # how far the foot is from the hip axis, measured along the floor
x = reach * cos(yaw)                  # x points straight out from the body, y to the left
y = reach * sin(yaw)
z = -(26 + 120 * sin(knee))           # z is up, so the foot is below the plate

    
Knee 0 is the leg horizontal, pointing outward. A positive knee tips the foot down. Hip yaw 0 is the leg straight out, and a positive yaw swings the foot counter-clockwise as seen from above. Two facts matter for everything that follows:

    
    
      
  • Height depends only on the knee. z has no yaw in it. So the body plate rides h = 26 + 120 sin(knee) above the floor whenever the foot is on the floor.
    • 
      
  • Yaw moves the foot on a circle. With the knee fixed, the foot swings around the hip axis at constant height. A foot on the floor can slide sideways on that circle, but it cannot move straight toward or away from the body without also rising or sinking.
    • 
    

    
Inverse kinematics for standing up. To ride at a height h, solve the height equation for the knee: knee = asin((h - 26) / 120). For 100 mm that is 38.1 degrees, the same value on every leg.

Why calibration
    
Tick 2048 is the middle of the servo's travel. It is not "leg straight out". When you screwed each horn on, it landed at some angle, and no two are the same. So for every servo you record one number, its zero tick: the reading when the leg is in the reference pose. After that the goal for any angle is:


ticks = zero + sign * angle * 4096 / 360

    
The sign is +1 when a positive servo turn gives a positive joint angle, and -1 when it does the opposite. All four legs are identical copies turned 90 degrees about the body, so one hip sign and one knee sign serve all four legs. Only the zeros differ. Lab 8.2 practised exactly this line.

    """Forward kinematics of one leg. (hip yaw, knee) in degrees -> foot (x, y, z) in mm.
    Origin = the hip axis at the underside of the body plate. x points straight out from the body, z points up."""
    t, p = math.radians(knee), math.radians(yaw)
    reach = KNEE_OUT + LEG * math.cos(t)          # how far the foot is from the hip axis, along the floor
    return reach * math.cos(p), reach * math.sin(p), -(KNEE_DROP + LEG * math.sin(t))


def foot_in_body(leg, yaw, knee):
    """Same, but measured from the body centre. x points FORWARD (between legs D and A), y points left."""
    x, y, z = foot_in_leg(yaw, knee)
    a = math.radians(LEG_ANGLE0 + 90 * leg)
    return (R_HIP + x) * math.cos(a) - y * math.sin(a), (R_HIP + x) * math.sin(a) + y * math.cos(a), z


def height_of(knee):
    """How high the body plate rides above the floor when the foot is on the floor at this knee angle (mm)."""
    return KNEE_DROP + LEG * math.sin(math.radians(knee))


def knee_for_height(h):
    """Inverse kinematics: the knee angle that puts the body plate h mm above the floor."""
    return math.degrees(math.asin((h - KNEE_DROP) / LEG))


def nod(servo_id, degrees=8, pause=0.6):
    """Make one servo nod: hold where it is, turn it a few degrees, turn it back, go limp. Used to show WHICH servo is which."""
    import bus
    start = bus.present_pos(servo_id)
    bus.torque(servo_id, True)                       # torque on first, so the servo holds the pose it is in
    bus.goal_pos(servo_id, start + round(degrees * TICKS_PER_DEG)); time.sleep(pause)
    bus.goal_pos(servo_id, start); time.sleep(pause)
    bus.torque(servo_id, False)


def lean_offsets(lifted, amount):
    """To lift leg `lifted`, its two neighbours slide their feet toward it by `amount` degrees of hip yaw.
    Returns {leg: yaw_offset}."""
    return {(lifted + 1) % 4: -amount, (lifted - 1) % 4: +amount}


def support_margin(points, com=(0.0, 0.0)):
    """Distance in mm from the centre of mass to the nearest edge of the polygon of feet on the floor.
    Negative means the centre of mass is OUTSIDE the polygon (the robot tips over). 3 or 4 points, in order."""
    if len(points) == 3:
        order = points
    else:                                          # sort 4 points around their centre
        cx = sum(p[0] for p in points) / len(points)
        cy = sum(p[1] for p in points) / len(points)
        order = sorted(points, key=lambda p: math.atan2(p[1] - cy, p[0] - cx))
    best, sign = 1e9, 1
    n = len(order)
    cross_sum = sum(order[i][0] * order[(i + 1) % n][1] - order[(i + 1) % n][0] * order[i][1] for i in range(n))
    orient = 1 if cross_sum > 0 else -1
    for i in range(n):
        (x0, y0), (x1, y1) = order[i][:2], order[(i + 1) % n][:2]
        ex, ey = x1 - x0, y1 - y0
        d = orient * (ex * (com[1] - y0) - ey * (com[0] - x0)) / math.hypot(ex, ey)   # positive = inside this edge
        best = min(best, d)
    return best


def body_turn(before, after, legs):
    """How far the body turned (degrees, counter-clockwise) when the planted feet `legs` went from pose `before` to pose `after`,
    and the worst foot slide (mm) left over. A foot that stays on the floor cannot move relative to the floor, so any
    leftover is the foot sliding."""
    P = [foot_in_body(l, *before[l])[:2] for l in legs]
    Q = [foot_in_body(l, *after[l])[:2] for l in legs]
    dot = sum(p[0] * q[0] + p[1] * q[1] for p, q in zip(P, Q))
    cross = sum(p[0] * q[1] - p[1] * q[0] for p, q in zip(P, Q))
    b = math.atan2(cross, dot)                      # how far the feet turned about the body centre
    slide = max(math.hypot(p[0] * math.cos(b) - p[1] * math.sin(b) - q[0], p[0] * math.sin(b) + p[1] * math.cos(b) - q[1]) for p, q in zip(P, Q))
    return -math.degrees(b), slide


def forward_sign(leg):
    """Which way a hip must turn to carry the foot of `leg` toward the front: -1 for the two left legs (A, B), +1 for the right legs (C, D).
    A hip swings its foot sideways to the leg, and a leg at 45 degrees has a forward part to that swing."""
    return -1 if math.sin(math.radians(LEG_ANGLE0 + 90 * leg)) > 0 else +1


def body_move(before, after, legs):
    """How far the body moves (forward mm, sideways mm) when the planted feet `legs` go from pose `before` to pose `after`, and
    the worst foot slide (mm) left over. Planted feet cannot move on the floor, so the body shifts by the average of what the feet
    did, and whatever is left over for each foot is that foot sliding."""
    P = [foot_in_body(l, *before[l])[:2] for l in legs]
    Q = [foot_in_body(l, *after[l])[:2] for l in legs]
    D = [sum(p[i] - q[i] for p, q in zip(P, Q)) / len(legs) for i in (0, 1)]
    slide = max(math.hypot(p[0] - q[0] - D[0], p[1] - q[1] - D[1]) for p, q in zip(P, Q))
    return D[0], D[1], slide

def compensated_knee(yaw, knee):
    """The hip swings the foot along a CIRCLE, so the foot drifts in toward the body as the hip turns away from straight out.
    This returns the knee angle that cancels the drift: the foot stays the same distance out from the leg's own straight-out line.
    The price: the knee also sets the height, so the foot rises or sinks a little instead."""
    x_out = KNEE_OUT + LEG * math.cos(math.radians(knee))            # how far out the foot is with the hip straight
    c = (x_out / math.cos(math.radians(yaw)) - KNEE_OUT) / LEG         # the reach the circle would need, turned back into a knee angle
    return math.copysign(math.degrees(math.acos(max(-1.0, min(1.0, c)))), knee)


def load_motion(path):
    """Read a motion file. Returns (joint_names, points) with points = [(time_from_start_seconds, [positions in degrees]), ...]."""
    with open(path) as f:
        m = json.load(f)
    return m["joint_names"], [(p["time_from_start"], p["positions"]) for p in m["points"]]


def motion_poses(names, points, stand_knee=40.0, straighten=False, dt=0.1):
    """Turn a motion into [(time, pose), ...] where pose = {leg: [yaw, knee]} for all four legs. Joints the motion does not name
    stay at yaw 0 and the standing knee. With straighten=True the motion is cut into steps of dt seconds and every leg that has
    both a hip and a knee gets compensated_knee() applied while its foot is in the air, so that part of the path is straight instead of a circle."""
    joints = {}
    for j, name in enumerate(names):
        kind, letter = name.split("_")                           # "hip_A" -> ("hip", "A")
        joints.setdefault(LEGS.index(letter), {})[kind] = j
    times = [t for t, _ in points]

    def at(t, j):                                                # straight line in time between the two points around t
        for (t0, p0), (t1, p1) in zip(points, points[1:]):
            if t0 <= t <= t1:
                return p0[j] if t1 == t0 else p0[j] + (p1[j] - p0[j]) * (t - t0) / (t1 - t0)
        return points[-1][1][j]

    grid = sorted(set(times) | ({round(k * dt, 6) for k in range(int(times[-1] / dt + 1e-9) + 1)} if straighten else set()))
    out = []
    for t in grid:
        pose = {leg: [0.0, stand_knee] for leg in range(4)}
        for leg, js in joints.items():
            if "hip" in js:
                pose[leg][0] = at(t, js["hip"])
            if "knee" in js:
                pose[leg][1] = at(t, js["knee"])
            if straighten and "hip" in js and "knee" in js:           # only while the foot is in the air: a foot on the floor must stay at floor height
                w = max(0.0, min(1.0, (stand_knee - pose[leg][1]) / 10.0))     # 0 on the floor, fading up to 1 when the knee is 10 degrees up
                pose[leg][1] += w * (compensated_knee(pose[leg][0], pose[leg][1]) - pose[leg][1])
        out.append((t, pose))
    return out


def margin_of_pose(pose, lifted=()):
    """Support margin for a pose {leg: (yaw, knee)}. Legs in `lifted` are off the floor."""
    pts = [foot_in_body(l, *pose[l]) for l in range(4) if l not in lifted]
    return support_margin(pts)

    """Joint angle -> servo ticks, using the zero you found in calibration:  ticks = zero + sign * angle * 4096 / 360."""

class Robot:
    """Eight servos on one bus. With dry_run=True nothing is sent anywhere: it only prints."""

    def __init__(self, dry_run=True, profile_velocity=0):
        self.dry_run = dry_run
        self.calib = load_calibration()
        if self.calib is None:
            if not dry_run:
                raise SystemExit("No quad_calib.json yet. Run quad_calibrate.py first.")
            print("(no quad_calib.json yet: using 2048 as every zero, fine for a dry run)")
            self.calib = {i: 2048 for i in HIP_ID + KNEE_ID}
        self.ids = HIP_ID + KNEE_ID
        if not dry_run:
            import bus
            self.bus = bus
            bus.open_bus()
            for i in self.ids:
                bus.write4(i, bus.PROFILE_VELOCITY, profile_velocity)    # 0 = as fast as it can, otherwise 0.229 rpm per unit
                bus.torque(i, True)

    def set_profile(self, value):
        """Servo speed limit register: 0 = as fast as it can, otherwise 0.229 rpm per unit."""
        if not self.dry_run:
            for i in self.ids:
                self.bus.write4(i, self.bus.PROFILE_VELOCITY, value)

    def goals(self, pose):
        g = {}
        for leg, (yaw, knee) in pose.items():
            g[HIP_ID[leg]] = joint_to_ticks(HIP_ID[leg], yaw, HIP_SIGN, self.calib[HIP_ID[leg]])
            g[KNEE_ID[leg]] = joint_to_ticks(KNEE_ID[leg], knee, KNEE_SIGN, self.calib[KNEE_ID[leg]])
        return g

    def go(self, pose):
        """Send all eight goals in ONE packet (sync write)."""
        g = self.goals(pose)
        if self.dry_run:
            return g
        self.bus.sync_goal(g)
        return g

    def close(self):
        if not self.dry_run:
            for i in self.ids:
                self.bus.torque(i, False)
            self.bus.close_bus()


class Mover:
    """Moves all eight joints together, at a speed you choose:
    you only say WHERE each joint should end up and HOW FAST, and this class sends a new set of goals 50 times a second
    until every joint has arrived. All eight joints start and stop together, in a straight line in joint space.
    The joint with the farthest to go moves at `speed` degrees per second; the others move proportionally slower."""

    def __init__(self, robot, rate=50):
        self.robot, self.rate = robot, rate
        self.cur = None
        self.updates = 0
        self.t0 = None

    def start(self, pose, seconds=2.5):
        """Go to the first pose slowly (the servos' own speed limit), then hand over to the 50 Hz loop."""
        self.cur = {l: list(pose[l]) for l in range(4)}
        self.robot.set_profile(30)
        self.robot.go(self.cur)
        if not self.robot.dry_run:
            time.sleep(seconds)
        self.robot.set_profile(0)

    def _tick(self):
        self.robot.go(self.cur)                      # ONE packet, all eight goals
        self.updates += 1
        if not self.robot.dry_run:                   # wait for the next tick on a fixed schedule
            if self.t0 is None:
                self.t0 = time.perf_counter() - 1.0 / self.rate
            wait = self.t0 + self.updates / self.rate - time.perf_counter()
            if wait > 0:
                time.sleep(wait)

    def go_to(self, pose, speed, settle=0.1):
        """Move every joint to `pose` ({leg: (yaw, knee)}), the farthest one at `speed` deg/s, then wait `settle` seconds."""
        start = {l: list(self.cur[l]) for l in range(4)}
        dist = max(abs(pose[l][j] - start[l][j]) for l in range(4) for j in range(2))
        n = math.ceil(dist / speed * self.rate) if dist > 1e-6 else 0
        for k in range(1, n + 1):
            for l in range(4):
                for j in range(2):
                    self.cur[l][j] = start[l][j] + (pose[l][j] - start[l][j]) * k / n
            self._tick()
        for _ in range(round(settle * self.rate)):   # let the servos finish before the next move
            self._tick()

    def go_for(self, pose, seconds, settle=0.0):
        """Move every joint to `pose` in exactly `seconds`, in a straight line, one packet per tick. This is the way a ROS 2
        joint trajectory works: each point says WHEN to arrive, not how fast to go."""
        start = {l: list(self.cur[l]) for l in range(4)}
        n = math.ceil(seconds * self.rate - 1e-9)
        for k in range(1, n + 1):
            for l in range(4):
                for j in range(2):
                    self.cur[l][j] = start[l][j] + (pose[l][j] - start[l][j]) * k / n
            self._tick()
        for _ in range(round(settle * self.rate)):
            self._tick()

    def seconds(self):
        """How long everything sent so far takes at this rate."""
        return self.updates / self.rate

How do other robots store a motion?
    
Before choosing a format I looked at how the people who make servo systems and robotics research labs store a motion. They all end up with the same thing: a list of poses, each with a time. The first two are the ones this lesson follows.

    

      
ROBOTIS MotionThe maker of your servos. A motion is a list of key-frames, each a pose plus its time on a timeline, and the robot interpolates between them (ROBOTIS e-Manual, Motion).

      
ROS 2The standard in research robotics. A JointTrajectory message has a list of joint_names, then points, each with positions and a time_from_start, the time at which to arrive at that point (JointTrajectoryPoint.msg). The controller that plays it can interpolate with splines. With positions only it falls back to straight lines between points, and the documentation discourages that because the speed jumps at every point (ros2_control, trajectory representation). That is what our player does for now. Module 13 is about doing better.

      
Poppy / pypotAn open-source robot platform from a research lab. You record a move by hand-guiding the robot while its positions are sampled 50 times a second, save it as a JSON file, and play it back later (Poppy notebook: record, save and play moves).

      
DeepMimic motion clipsA reference motion for learning-based control, from a university graphics and robotics group. It is a JSON file with a Loop flag ("wrap" for a cycle) and a list of Frames. Each frame starts with its duration in seconds, followed by the joint angles, in radians for a hinge joint such as a knee (DeepMimic README).

      
Petoi Bittle and NybbleA hobby kit. A gait is an array: a short header, then one row of joint angles per frame, played round and round (Petoi skill guide).

      
SunFounder crawler kitA hobby kit. A hand-written sequence of set_site(leg, x, y, z) calls, each followed by wait_all_reach(). A pose is where the feet go, and the speed is set separately. We borrow its turn gait in Module 12, not its way of storing moves.

    

    
What they share: joint angles, one pose per row, and a time. We use joint angles with arrival times, which is exactly the ROS 2 shape and close to a ROBOTIS key-frame. It needs no inverse kinematics. The Module 10 walk uses speeds instead of times because that is easier to tune by feel, and it is the same idea underneath.

Step 2: the hip draws a circle
    
Look at the foot's path from above in Lab 9.1. A hip swing does not move the foot in a straight line. The foot is a fixed distance from the hip axis, so it moves on a circle. As the hip turns away from straight out, the foot drifts in toward the body. The drift is small for a small swing (about 3 mm at 12 degrees), and large for a long one (about 29 mm at 40 degrees).

    
You can cancel the drift. The foot's distance out depends on the knee, so if the knee eases the foot outward as the hip turns, the path comes out straight. The catch: the knee also sets the foot's height. This leg has only two joints, so it cannot do both. A straight path costs a foot that rises and sinks a little. A foot on the floor must keep its height, so on the floor you keep the circle and accept a small skid. In the air, a bit of height wobble does not matter, so you straighten the path only there. That is what the formula below does, and what the checkbox in Lab 9.2 turns on.


x_out = 32 + 120 * cos(knee)                    # how far out the foot is now
reach = x_out / cos(yaw)                         # the reach that would keep the foot on a straight line
knee_new = acos((reach - 32) / 120)              # the knee that gives that reach

A very basic walk: lift, swing, lower, push

  
The simplest way to walk is one leg at a time. Lift a leg, move it forward, put it down, and when every leg has had its turn, push every foot backward together so the body slides forward. It looks like a toy soldier. It is also how the first walking robots worked, and you can reason about it with a pencil.

  
By the end: a stop-and-go walk that keeps the robot's weight inside its feet at every moment, and a clear reason for each of the five phases.


  
The trap: three feet are not enough
    
Lift one leg and the robot stands on the other three. It stays up only if its centre of mass is inside the triangle those three feet make. Look at the layout: the legs sit at the four corners. Lift the front-left leg (A) and the other three feet are rear-left, rear-right and front-right. The rear-left and front-right feet are on opposite corners, so the line between them passes exactly through the centre. The margin is zero. Any wobble and it tips. The same is true for whichever leg you lift.

    
The fix is a lean. Before you lift leg A, the two legs beside it (B and D) slide their feet a little toward it, which moves that edge of the triangle past the centre. In general: the two neighbours of the lifted leg reach toward it first. In the code that is lean_offsets(leg, amount). Lab 10.1 shows the margin in millimetres. It is zero with no lean, and a lean of about 20 degrees gives a comfortable 17 mm.


  
Which feet can push?
    
From Module 8: a foot on the floor can only slide along its circle around the hip. Every leg here sits at 45 degrees to the direction of travel, so each hip swings its foot along a line that points half backward and half sideways. The backward half pushes the body forward. The sideways half has nothing to push against: the left legs want to shove the body one way, the right legs the other, and the two cancel. Left over, every foot has to skid sideways across the floor by about as much as the body moves forward.

    
So this gait is honest about a compromise: with two joints per leg, the feet skid. At stroke 12 the body moves about 36 mm per step and each foot skids about 36 mm. Use smooth, hard feet (printed PLA on a laminate floor works) and keep the stroke small. Lab 10.1 shows how far they skid. Better gaits need a third joint in each leg, which is how the SunFounder kit can move a foot in a straight line. That is a good reason to keep this one very basic.

from quad import Robot, Mover, lean_offsets, describe, lifted_legs, forward_sign, body_move, LEGS

DRY_RUN = True
CYCLES = 2            # how many steps to take
STAND_KNEE = 40.0     # knee angle with the foot on the floor (body about 100 mm high)
LIFT_KNEE = 15.0      # knee angle with the foot in the air
STROKE = 12.0         # every hip swings between +STROKE and -STROKE of yaw around its standing position
LEAN = 20.0           # how far the neighbours slide their feet to catch the weight
ORDER = (0, 2, 3, 1)  # legs A, C, D, B (front-left, rear-right, front-right, rear-left): each lifted foot is far from the last one
LEG_SPEED = 90.0      # deg/s for lifting, swinging and lowering a foot (nothing heavy rides on it)
BODY_SPEED = 30.0     # deg/s while all feet are on the floor: leaning, centring, pushing. Slow, so nothing slips
SETTLE = 0.15         # seconds to wait after each move so the servos catch up


def walk_keyframes():
    """Return a list of (name, pose, speed). pose = {leg: (hip_yaw, knee)} for all four legs."""
    S, K, L = STROKE, STAND_KNEE, LEAN
    pose = {leg: [-forward_sign(leg) * S, K] for leg in range(4)}     # every foot starts at the BACK of its stroke
    frames = []

        frames.append((name, {l: tuple(v) for l, v in pose.items()}, speed))

    snap("stand", BODY_SPEED)
    for leg in ORDER:
        offsets = lean_offsets(leg, L)
        for l, o in offsets.items():
            pose[l][0] += o

        pose[leg][1] = LIFT_KNEE;                    snap(f"lift leg {LEGS[leg]}", LEG_SPEED)

        for l, o in offsets.items():
            pose[l][0] -= o
        snap("centre again", BODY_SPEED)
    for leg in range(4):
        pose[leg][0] = -forward_sign(leg) * S
    snap("push: body moves forward", BODY_SPEED)
    return frames

What this lab simplifies

Turn in place

  
Turning is the one motion this leg design does almost perfectly. This gait uses the same sequence as the turn in the SunFounder crawler kit: lift one foot, move all the feet to their new places at once, put the foot down. The three feet that stay on the floor are what turn the body.

  
By the end: a turn gait that rotates the body about 19 degrees per cycle with almost no foot sliding, and a reason why moving the feet together is what turns the body.


  
The sequence, one stage at a time
    
The legs take turns in the air: A, then B, then C, then D, counter-clockwise around the body. Each stage is three moves:

    
    
      
  1. Lift the leg whose turn it is. Only the knee moves.
    2. 
      
  2. Sweep. All four hips move at the same time. Each of the three feet on the floor swings back by STROKE degrees. A foot on the floor cannot move relative to the floor, so what actually happens is that the body turns underneath them. The foot in the air swings forward by 3 x STROKE to the front of its stroke, ready to come down.
    3. 
      
  3. Lower that leg.
    4. 
    

    
Every foot spends three stages on the floor, being swept back STROKE each time, and one stage in the air, going forward 3 x STROKE. After four stages every leg is exactly where it started, and the body has turned four times.

    
Why there is no lean here. In Module 10, the legs sat in matching places and the weight sat on the edge of the support triangle, so we had to lean. Here the four feet are at different points in their strokes: one at the front, one a third of the way back, and so on. That stagger moves the edge of the support triangle off the centre of mass automatically, and by the same amount at every lift. It works only when the legs take their turns in the order that matches the direction of the turn. Lab 12.1 shows the margin. SunFounder's kit gets its stagger the same way, from feet that alternate between two positions along the body.


  
What you were asking about: set_site
    
The kit's code says set_site(leg, x, y, z). That sets where the foot should end up, in millimetres from that leg's hip, and a timer service then moves the foot there in a straight line at the speed in move_speed, 50 times a second. Its three servos per leg turn a foot position into three joint angles. Your legs have two servos, so the equivalent of set_site here is a pose: a hip yaw and a knee angle for each leg. The Mover from Module 10 moves them in the same straight-line way.

  lower  that leg goes down.

Because each leg is a different distance through its stroke, the feet are staggered, and that stagger is what keeps the
centre of mass inside the three feet that are down. No extra lean is needed.
"""
from quad import Robot, Mover, describe, lifted_legs, body_turn, LEGS

DRY_RUN = True
TURN_LEFT = True      # False turns the other way
CYCLES = 2
STAND_KNEE = 40.0     # knee angle with the foot on the floor
LIFT_KNEE = 15.0      # knee angle with the foot in the air
STROKE = 8.0          # how far each planted hip swings per stage, degrees. Bigger = faster turn and safer, but a bigger swing in the air
LEG_SPEED = 90.0      # deg/s for lifting and lowering
TURN_SPEED = 40.0     # deg/s for the sweep (the foot in the air moves at this speed, the others slower, so they all arrive together)
SETTLE = 0.15


def turn_keyframes():
    """Return a list of (name, pose, speed). pose = {leg: (hip_yaw, knee)} for all four legs."""
    S, K = STROKE, STAND_KNEE
    d = 1 if TURN_LEFT else -1                    # +1: planted hips swing toward smaller yaw
    order = (0, 1, 2, 3) if TURN_LEFT else (0, 3, 2, 1)
    top = 1.5 * S                                 # the front of the stroke. The stroke runs from +1.5 S down to -1.5 S
    # steady state before stage 0: the leg lifted last is at the top, the one lifted first is at the bottom
    pose = {}
    for leg in range(4):
        age = (-order.index(leg) - 1) % 4         # stages since this leg was in the air
        pose[leg] = [d * (top - S * age), K]
    frames = []

    def snap(name, speed):
        frames.append((name, {l: tuple(v) for l, v in pose.items()}, speed))

    snap("stand ready", LEG_SPEED)
    for leg in order:
        pose[leg][1] = LIFT_KNEE;  snap(f"lift leg {LEGS[leg]}", LEG_SPEED)
        for other in range(4):
            pose[other][0] += d * 3 * S if other == leg else -d * S
        pose[leg][0] = d * top                    # the foot in the air goes to the front of its stroke
        snap(f"sweep: leg {LEGS[leg]} returns, the others turn the body", TURN_SPEED)
        pose[leg][1] = STAND_KNEE; snap(f"lower leg {LEGS[leg]}", LEG_SPEED)
    return frames

Module 13 of 13 · about 45 minutes
Many motors at once: smooth motion

  
The walk so far goes to a pose, waits, goes to the next pose. Each pause is a stop, and each stop makes the robot rock. Smooth walking needs two things: the eight goals have to arrive together, and each joint has to follow a curve through the key poses instead of stopping at each one.

  
By the end: eight goals sent in one packet fifty times a second, each joint gliding through the key poses of the walk, and a number for the fastest any joint moves.


  
Part 1: one packet, not eight
    
Writing a goal to one servo costs a 16-byte packet out and an 11-byte status packet back. Eight servos means eight round trips, and the last leg moves a long time after the first. A sync write is one instruction packet to many servos at once: a 14-byte header and 5 bytes per servo (an ID and a 4-byte goal). No replies come back, and all the servos start together. sync_goal() in bus.py already does this, and Robot.go() uses it for all eight.

    
Time on the wire is bytes times 10 bits (8 data bits plus start and stop) divided by the baud rate. The lab adds 1 ms for the USB hop per call and 0.5 ms for the servo's return delay per reply.

Part 2: a curve through the key poses
    
The key poses are the same ones as Module 10. Give each joint its list of angles, one per pose, a fixed time apart. There are three ways to move between them:

    
    
      
  • Hold, then jump. Send the next pose and let the servo race to it at full speed. The simplest way, and the roughest.
    • 
      
  • Straight lines. A joint moves at constant speed between poses. This is what Mover in Module 10 does. Better, but its speed changes suddenly at every pose. The servo and the leg feel each change as a jerk.
    • 
      
  • A smooth curve. Speed changes gradually, and a joint that turns around (a knee that goes up and then down) slows to zero at the top, with no overshoot. This is a monotone cubic curve, called pchip. It is about 20 lines in quad_smooth.py, with no libraries.
    • 
    

    
Then read the curves fifty times a second and send each reading as one sync write. The loop waits for fixed times (start + n x 0.02), not "sleep 0.02 s" after every send. Sleeping after the work adds the work's time on top, and the whole walk slowly runs late.

def pchip(ts, ys):
    """Smooth curve through the points (ts[i], ys[i]) that never overshoots between them. Returns f(t) -> (value, slope)."""
    n = len(ts)
    h = [ts[i + 1] - ts[i] for i in range(n - 1)]
    d = [(ys[i + 1] - ys[i]) / h[i] for i in range(n - 1)]
    m = [0.0] * n
    for i in range(1, n - 1):
        if d[i - 1] * d[i] > 0:                    # same direction on both sides: blend the slopes
            w1, w2 = 2 * h[i] + h[i - 1], h[i] + 2 * h[i - 1]
            m[i] = (w1 + w2) / (w1 / d[i - 1] + w2 / d[i])
        # else: the joint turns around here (a peak), so its speed is zero here
    m[0], m[-1] = d[0], d[-1]
    if d[0] == 0:
        m[0] = 0.0
    if d[-1] == 0:
        m[-1] = 0.0

    def f(t):
        t = min(max(t, ts[0]), ts[-1])
        i = min(max(max(k for k in range(n - 1) if ts[k] <= t), 0), n - 2)
        s = (t - ts[i]) / h[i]
        h00, h10, h01, h11 = 2 * s**3 - 3 * s**2 + 1, s**3 - 2 * s**2 + s, -2 * s**3 + 3 * s**2, s**3 - s**2
        v = h00 * ys[i] + h10 * h[i] * m[i] + h01 * ys[i + 1] + h11 * h[i] * m[i + 1]
        ds = (6 * s**2 - 6 * s) * ys[i] + (3 * s**2 - 4 * s + 1) * h[i] * m[i] + (-6 * s**2 + 6 * s) * ys[i + 1] + (3 * s**2 - 2 * s) * h[i] * m[i + 1]
        return v, ds / h[i]
    return f


def build_curves():
    frames = (quad_walk.walk_keyframes() if GAIT == "walk" else quad_turn.turn_keyframes())[1:]   # skip the slow 'stand' pose
    stand_knee = quad_walk.STAND_KNEE if GAIT == "walk" else quad_turn.STAND_KNEE
    frames = frames + [frames[0]]                    # close the loop: end where you began
    ts = [i * TIME_PER_POSE for i in range(len(frames))]
    curves = {}
    for leg in range(4):
        for j, name in enumerate(("hip", "knee")):
            curves[(leg, j)] = pchip(ts, [fr[1][leg][j] for fr in frames])
    return curves, ts[-1], frames[0][1], stand_knee

"""Log commanded and measured position for Optional B. Saves run1.csv."""
import csv
import math
import time
from bus import open_bus, close_bus, torque, goal_pos, present_pos, to_steps, to_deg

SERVO = 2                  # the pitch joint, with nothing attached to the horn yet
DURATION = 3.0             # seconds


def command(t):
    """Same command as Optional B, in radians: a step, a rest, a small step, then a 2 Hz sine."""
    if t < 0.1: return 0.0
    if t < 0.7: return 0.5
    if t < 1.2: return 0.0
    if t < 1.5: return 0.25
    if t < 2.5: return 0.25 + 0.2 * math.sin(2 * math.pi * 2.0 * (t - 1.5))
    return 0.25


open_bus()
rows = []
try:
    torque(SERVO, True)
    goal_pos(SERVO, to_steps(0))
    time.sleep(1.0)
    start = time.perf_counter()
    while True:
        t = time.perf_counter() - start
        if t > DURATION:
            break
        cmd = command(t)
        goal_pos(SERVO, to_steps(math.degrees(cmd)))
        meas = to_deg(present_pos(SERVO))      # read straight after writing
        rows.append((t, cmd, math.radians(meas)))
finally:
    torque(SERVO, False)
    close_bus()

with open("run1.csv", "w", newline="") as f:
    w = csv.writer(f)
    w.writerow(["t", "cmd_rad", "meas_rad"])
    w.writerows(rows)
print(f"saved {len(rows)} rows, about {len(rows) / DURATION:.0f} samples per second")

"""Fit the Optional B model to the CSV that log_step.py saved."""
import numpy as np
from scipy.optimize import least_squares

t, cmd, pos = np.loadtxt("run1.csv", delimiter=",", skiprows=1, unpack=True)


def model(p, t, cmd):
    delay, wn, zeta, vmax = p
    th = np.zeros_like(t)
    w = 0.0
    for k in range(1, len(t)):
        dt = t[k] - t[k - 1]                        # real logs are not evenly spaced
        c = np.interp(t[k] - delay, t, cmd)         # the command, delayed
        w += (wn**2 * (c - th[k - 1]) - 2 * zeta * wn * w) * dt
        w = np.clip(w, -vmax, vmax)
        th[k] = th[k - 1] + w * dt
    return th


fit = least_squares(lambda p: model(p, t, cmd) - pos,
                    x0=[0.01, 30, 0.7, 6.0],
                    bounds=([0, 5, 0.1, 1], [0.05, 100, 2.0, 8]))
print({k: round(float(v), 3) for k, v in zip(["delay", "wn", "zeta", "vmax"], fit.x)})
print("RMS error (rad):", float(np.sqrt(np.mean((model(fit.x, t, cmd) - pos) ** 2))))

    
Always plot the fit over the data before you trust the numbers. One run can fit well and still be wrong. Log a second run with a different command and see whether the same numbers hold.
